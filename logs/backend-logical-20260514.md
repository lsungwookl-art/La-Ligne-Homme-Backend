# 설계 목적
- 앞으로 들어올 수 많은 종류의 쇼핑몰에도 적용이 가능한 범용성.
- 최소한의 수정 및 추가 업데이트로 시대의 변화나 흐름에도 대처가 가능한 유연성과 유지 보수성. 
- 위 두가지를 갖춰 앞으로의 외주 의뢰에 효율적 대처 : 개념설계에서 소비자와 의사 소통의 주도권 확보 -> 의뢰인의 서비스 만족도 충족 -> 프로젝트 완료까지 기간과 소모 비용 최적화.

## 범용성 극대화 전략
1. 도메인 주도 설계(DDD) 기반의 모듈화
    - User, Order, Product, Review 등 각 도메인을 격리 : 모듈화하여 소핑몰의 성격에 따른 재사용성 추가 확보.
    - 도메인 디벤트(Domain Event)활용 : 도메인 간의 결합도를 더 낮추기 위해, 직접적인 호출 대신 event를 던지는 구조를 고려. 예를 들어 '주문 완료' 시 '포인트 적립'이나 '알림 발송'이 일어나야 한다면, 주문(Order) 도메인이 서비스를 직접 부르는게 아니라 OrderCompleted 이벤트를 발행하는 방식.
2. 인터페이스 기반의 추상화(Plug & Play)
    - 결제(Payment), 알림(Notification), 파일 업로드(Storage) 같은 외부 연동 기능은 인터페이스로 정의 
    - 만약 결제 방식의 변경시 인터페이스 구현체만 변경 -> 재사용성및 유지 보수성
3. 메타 데이터 구조 채택 (Dynamic Properties)
    - 테이블에 고정된 컬럼을 두지 말고, 옵션이나 상세 속성을 JSON타입이나 별도의 Attribute 테이블로 관리
    - 쇼핑몰의 취급 상품이 바뀌어도 DB스키마 수정 없이도 사용가능 -> 범용성의 핵심

- 이번 프로젝트에서 작성하는 모든 코드는 `라이브러리화`가 가능하게 작성
    - BaseResponse & GlobalException : 모든 프로젝트에 공통으로 들어갈 응답 규격과 에러 핸들링 표준화
    - Security Config: JWT 기반의 보안 설정을 조금만 수정해도 바로 쓸 수 있도록 모듈화하여 개발시간 단축
4. Soft Delete 및 히스토리 관리(데이터 무결성)
    - 범용적인 상거래 시스템에서 데이터는 삭제하는 것이 아니라 `상태`가 변하는 것. is_deleted 컬럼을 공통 엔티티(BaseEntity)에 포함하고, 상품 가격 변동이나 재고 이력 등을 별도의 Log 테이블로 관리. 
    - 서비스 주체의 의도치 않은 행위 혹은 정보 요구에 즉각 대응 가능 : 유지보수성 확보
5. API 버전 관리 전략(Versioning)
    - 유지보수성을 위해 초기부터 URL에 버전을 명시(예: /api/v1/...)
    - 라이브러리 업데이트를 하더라도 기존 고객들의 서비스가 멈추지 않게 하려면 버전 관리는 필수. -> 시대의 변화나 흐름에 맞춰 로직을 대대적으로 개편해도, 구버전과 신버전을 동시에 서비스하며 점진적 교체 가능
